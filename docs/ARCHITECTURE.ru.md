# Архитектура KuzTDS

Актуально на 2026-09-30. Снимок прогресса — `docs/STATUS.md`.

## Четыре бинарника
- `cmd/engine` (:8080) — горячий путь (обработка трафика). Долгоживущий процесс.
- `cmd/admin` (:8090) — REST API + встроенный SPA (`internal/admin/web`, go:embed).
- `cmd/cron` — фоновый сервис (`internal/cron`): обновление списков и гео-баз,
  VirusTotal, мониторинг диска, очистка, Telegram. Порта нет.
- `cmd/apiclient` (:9090) — клиент для лендинга/донора:
  собирает данные посетителя → зовёт движок `?api=` → применяет ответ.

Общие пакеты — в `internal/`.

## Жизненный цикл запроса в engine

```
HTTP-запрос
  │
  ├─ постбэк? (?pb=KEY&cid=&profit=) → store.RecordPostback, выход
  │
  ├─ realip middleware (XFF/CF только от trusted_proxies)
  │
  ├─ api-режим? (?api=base64(JSON), проверка KUZTDS_API_KEY)
  │     да → вход (ip/ua/ref/lang/uniq/key/domain/cf_country/pars/id) из запроса
  │
  ├─ ipindex.Lookup(ip, ip_blacklist)        → в блэклисте: 403
  │
  ├─ группа по id/алиасу (первый сегмент пути или api.id); нет → trash-режим
  │
  ├─ антифлуд (Redis): N запросов/IP за окно
  │
  ├─ detect.Parse(ua) → device/OS/браузер/бренд
  ├─ geo.Resolve(ip) → страна/город/регион/часовой пояс + ASN/организация ;
  │     CF-IPCountry только если запрос пришёл через доверенный прокси ;
  │     настройка группы `geo` решает, какой источник страны побеждает
  ├─ ipindex.Lookup(ip, wap) → оператор
  │
  ├─ уникальность: cookie | Redis SETNX
  │
  ├─ router.Select(group, visitor)           → выбор потока по правилам-данным
  │     тип "group" → взять целевую группу и выбрать снова (≤ 3 переходов);
  │     событие запоминает первый передавший поток в `via`
  │
  ├─ detect ботов ПО ТОГГЛАМ ВЫБРАННОГО ПОТОКА (UA/referer/PTR/empty/ipv6/
  │     ua_blacklist/IP-списки SE/save_ip) → bot_redirect (или skip)
  │
  ├─ separation (ключ→выход, список в памяти) · remote (загрузка [REMOTE]; подстановка ПОСЛЕ макросов) · chance ·
  │     распределение ||| (random/rotator/evenly) · api_mac
  │
  ├─ render: макросы + тип редиректа (CURL — загрузка+find/replace; api — JSON);
  │  тело [REMOTE] подставляется ПОСЛЕ раскрытия макросов и не сканируется
  │
  ├─ save_keys / keys_se (сбор ключевых слов в файлы)
  │
  └─ logbuf.Push(event) → async-батч в ClickHouse (ответ не ждёт)
```

Важно: детект ботов идёт ПОСЛЕ выбора потока — по тогглам
конкретного потока; bot_redirect отдаёт ботам отдельный вывод.

## Пакеты internal/
| Пакет | Роль |
|-------|------|
| `ipindex` | CIDR-индекс O(log n) + менеджер списков с hot-reload |
| `config` | модель групп/потоков (правила-данные) + JSON-загрузчик с алиасами, атомарная подмена при hot-reload |
| `seplist` | списки separation («ключ;out») в памяти, с hot-reload |
| `geo` | Resolver: `DB` — базы City/Country + ASN в формате MaxMind, читаются в память и атомарно подменяются при изменении файлов — или `Nop`; помощники для смещения от UTC |
| `cron` | фоновые задачи, их конфиг (JSON), файл состояния и очередь «запустить сейчас» |
| `atomicfile` | запись во временный файл в том же каталоге, затем переименование |
| `detect` | устройство + OS/браузер/бренд (mileusna/useragent) + боты, сигнатуры с hot-reload |
| `router` | выбор потока (предикаты): lang/country/…/os/browser/brand/asn/org/timezone/get/schedule/limit; `Why` называет правило, отклонившее посетителя |
| `render` | макросы вывода + все типы редиректа |
| `fetch` | HTTP-клиент с TTL-кэшем в памяти (CURL-редирект, `[REMOTE]`) |
| `store` | ClickHouse (логи/постбэки/статистика) + Redis (uniq/limit/firewall/rotate/сессии) |
| `logbuf` | асинхронный буфер событий → батч-вставка в ClickHouse |
| `security` | argon2id, токены/сессии, CSRF, constant-time |
| `server` | realip middleware (trusted proxies) |
| `admin` | HTTP-хендлеры, файловые хранилища (группы/.dat/ключи), проверка IP, симулятор посетителя, конфиг cron, встроенный SPA |

## Ключевые принципы
1. **Состояние в памяти процесса** (IP-индексы, конфиг, сигнатуры, гео-базы),
   обновление в фоне — решение о маршрутизации не читает файлов.
2. **Горячий путь без лишнего блокирующего I/O**: логи async; счётчики Redis;
   внешние вызовы (CURL/remote/PTR) с таймаутами.

   Исключение — три опциональные фичи, которые *действительно* ходят в файловую
   систему на каждом запросе, где включены: `save_keys`/`save_keys_se` дописывают
   строку (`appendKey`), `save_ip` дописывает IP краулера (`saveBotIP`, одна
   запись на IP за время жизни процесса), а макросы `[RANDLINE]`/`[RANDDFL]`
   читают файл или каталог (`render/macros.go`). Включайте их, понимая, что это
   размен пропускной способности на фичу; всё остальное — включая списки
   separation с #17 — остаётся в памяти.
3. **Правила — это данные** (список предикатов, прогоняемых в цикле).
4. **Атомарная замена индексов** при hot-reload (`atomic.Pointer`).

## Конфигурация
- Конфиг групп: JSON-файл `KUZTDS_GROUPS_FILE` (источник истины).
- Engine держит группы в памяти и перечитывает файл при его изменении — по тому
  же тикеру `KUZTDS_RELOAD_INTERVAL`, что и `.dat`-списки. Рестарт не нужен.
- Admin читает/пишет файл при запросах к `/api/groups` (live). Один и тот же
  файл должен быть указан и движку, и админке.
- Гео-базы: `KUZTDS_GEO_DB` (City или Country) и `KUZTDS_ASN_DB`, в формате
  MaxMind. Держатся в памяти и перечитываются при изменении файлов — именно так
  скачанное cron-сервисом вступает в силу.
- Секреты/настройки — через переменные окружения `KUZTDS_*` (см. `docs/USAGE.md`).
  Исключение — конфиг cron, который правит админка: в нём токен Telegram и
  API-ключи, он пишется с правами `0600` и исключён из git.

## Cron-сервис
У `cmd/cron` нет соединений ни с движком, ни с админкой — только файлы:

- **конфиг** `KUZTDS_CRON_FILE` (JSON): пишется админкой (`PUT /api/cron`),
  перечитывается сервисом на каждом тике (5 с) и валидируется до любого запуска;
- **состояние** `<config>.status.json`: пишется сервисом после каждой задачи —
  последний запуск, результат, следующий запуск, heartbeat — и читается админкой;
- **запустить сейчас** `<config>.run`: админка дописывает имя задачи, сервис
  забирает файл на следующем тике;
- **результат**: `.dat`-списки в `KUZTDS_DATA_DIR`, базы по путям
  `KUZTDS_GEO_DB` / `KUZTDS_ASN_DB`, файл групп — всё это движок подхватывает
  через hot-reload.

Каждая задача выполняется в своей горутине, не более одного экземпляра
одновременно, так что медленный проход VirusTotal не задерживает проверку
диска. Расписание переживает рестарт (в файле состояния хранится время
следующего запуска каждой задачи). Всё скачанное проверяется до того, как
заменит рабочий файл: источник IP без единого адреса отклоняется, база
открывается, и её тип сверяется со слотом, для которого она предназначена.
Запись идёт через временный файл и переименование.

## Хранилище
- **ClickHouse**: `events` (логи) + `postbacks`. Партиции по дате, TTL для
  авто-очистки (миграции в `migrations/clickhouse`). Сетевые колонки (`asn`,
  `org`, `timezone`, `via`) добавлены позже: движок и админка при старте
  выполняют `ALTER … ADD COLUMN IF NOT EXISTS` и откатываются на старый набор
  колонок, если он отклонён, — поэтому обновление не требует ручной миграции и
  не может стоить событий.
- **Redis**: uniq / limit / firewall / rotate (evenly) / сессии админки / rate-limit логина.

## Безопасность (детали — `docs/SECURITY.md`)
realip с доверенными прокси · argon2id + серверные сессии + CSRF · параметризованные
запросы CH · только JSON · секреты вне VCS · экранирование вывода.

## Наблюдаемость (план/частично)
`slog` структурные логи и `/healthz`, который отдаёт счётчики потерянных логов в
`X-Events-Lost` / `X-Events-Lost-Detail` (`full` — переполнен входной канал, не
успевает накопитель; `queue` — переполнена очередь батчей, не успевает писатель;
`insert` — хранилище отвергло батч; `late` — запись пришла во время остановки),
чтобы падающий ClickHouse не выглядел как здоровый. Те же числа пишутся в лог при
выходе. `/metrics` (Prometheus) и `pprof` — в TODO.
