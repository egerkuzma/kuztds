# STATUS — где мы и как продолжить

Снимок на 2026-09-30. Для деталей: `docs/USAGE.md`, `TODO.md`.

## Готово (в `main`, тесты зелёные)
- **Фазы 1–7**: ipindex (+hot-reload), realip, geo (mmdb/Nop) + detect
  (устройство/OS/браузер/бренд + боты), router (выбор потока по правилам),
  store/logbuf (ClickHouse + Redis), admin API + встроенный SPA, рендер +
  JSON-конфиг групп.
- **Блок 1** — per-stream бот-тогглы + bot_redirect/out_bot/b_header.
- **Блок 2** — separation, распределение rotator/evenly/random, chance, trash.
- **Блок 3** — CURL-редирект+кэш, remote_pars (`[REMOTE]`), api_mac.
- **Блок 4** — постбэк `?pb=`, сбор ключей (save_keys/keys_se), экраны
  конверсий и ключей.
- **Блок 6** — api-клиент (`cmd/apiclient`) + приём `?api=` движком.
- **Блок 7** — экспорт логов CSV, источники (домены), очистка логов группы,
  перестановка потоков ↑/↓.
- **UI (переделан 2026-09-08; заменён 2026-09-30, см. ниже)**: стиль GitHub (Primer) в **светлой и тёмной**
  темах (переключатель в топбаре, запоминается в браузере, до выбора —
  системная настройка). **Дашборд** отвечает на вопрос «что работает»: плитки
  KPI, включая конверсии / профит / CR, двухцветный график с наведением и
  **таблица результативности по группам и потокам** (новый
  `GET /api/stats/performance`: события и постбэки агрегируются по
  группе/потоку в хранилище и сливаются в Go). **Группы** показывают группу как
  **водопад** потоков в порядке перебора — по правилу на строку
  (переключатель, чипы условий, выход, боты, хиты / боты / конверсии),
  перетаскивание для смены порядка, строка «no match → group default» со
  своими цифрами, настройки группы раскрываются по кнопке. **Редактор потока**
  — «КОГДА → КУДА»: показаны только настроенные условия, остальные из 19 видов
  — за «Add condition»; боты — чипы-переключатели; редкое (шанс, separation,
  `[REMOTE]`, CURL, API mac) свёрнуто в Advanced. Инварианты прежнего
  мастер-детейла сохранены: одна панель, обе стороны скроллятся внутри себя,
  без `scrollIntoView`, метка несохранённого, подтверждение при уходе и
  закрытии, `Ctrl`/`Cmd`+`S`. Кроме того, в настройки группы выведены
  `save_keys` / `save_keys_se` (прежняя форма их не несла, и каждое сохранение
  сбрасывало оба в false). Тесты: якоря в `web_test.go` + `-tags=uitest`;
  интеграционный тест теперь покрывает `Performance` и `DeleteGroupLogs`.
- **Фикс (2026-09-08)**: «Clear logs» удалял по `group_name`, а панель
  присылала **ID** группы — при заданном отображаемом имени не удалялось
  ничего. `DeleteGroupLogs` теперь ключуется по `group_id` (`clickhouse.go`).
- **2026-09-30 — гео, cron, flows** (одна ветка):
  1. **Гео из баз в формате MaxMind.** `geo.DB` читает в память City/Country-
     файл (`KUZTDS_GEO_DB`) и ASN-файл (`KUZTDS_ASN_DB`) и подменяет их при
     изменении файлов; битая замена никогда не обнуляет данные. Новые условия
     потока: `asn`, `org`, `timezone` (смещение от UTC или имя зоны), `get`
     (параметр URL). Новые макросы `[ASN] [ORG] [TIMEZONE] [UTC]`. События
     несут `asn/org/timezone` (колонки добавляются при старте; старая схема
     допускается). Проверено на тестовых базах GeoLite2 и вживую на DB-IP Lite
     (в ней нет часового пояса и ISO-кодов регионов — регион подставляется по
     имени). Поиск декодирует только те поля, которые использует: около 0.4 мкс
     и 5 аллокаций на City + ASN (`make bench`) вместо 15 аллокаций, когда
     локализованные имена читались как map.
  2. **`CF-IPCountry` доверяют только через доверенный прокси**, а настройка
     группы `geo` теперь решает, какой источник побеждает (`cf` = сначала
     заголовок, иначе сначала база). Раньше заголовок читался от любого
     посетителя, а настройка ничего не делала.
  3. **Блок 5 — cron-сервис** (`cmd/cron`, `internal/cron`): IP-списки ботов
     (обычные, с секциями, JSON Google/Bing; replace/merge), загрузка гео-баз
     (`.mmdb` / `.gz` / `.tar.gz`, проверка до переименования,
     `If-Modified-Since`, когда есть что сохранять), VirusTotal (один алерт на
     домен, опциональное выключение потоков; неизвестный домен считается
     чистым, исчерпанная квота останавливает проход), место на диске, очистка
     ключей, алерты о конверсиях, Telegram. Конфиг, состояние и «запустить
     сейчас» — через файлы; секреты в API маскируются. Прогнан от начала до
     конца на стенде против настоящих эндпоинтов Google, Bing и DB-IP. По пути
     найдена одна гонка — тестом, падавшим раз на двенадцать прогонов:
     heartbeat и завершающаяся задача оба писали файл состояния, и более старый
     снимок мог записаться последним — задача тогда выглядела «выполняющейся»
     после завершения, а через рестарт запускалась заново. Записи теперь
     упорядочены; регрессионный тест без фикса падает пять раз из шести.
  4. **Связи групп**: тип редиректа `group` передаёт посетителя в другую группу
     (≤ 3 переходов, битые ссылки отвечают как неизвестная группа); событие
     запоминает передавший поток (`via`), и `Performance` засчитывает визит и
     ему.
  5. **Admin API**: `GET /api/lookup`, `POST /api/simulate` (проводит
     посетителя через группы, присланные в запросе; `router.Why` называет
     отклонившее правило), `GET|PUT /api/cron`, `POST /api/cron/run`.
     CSV-экспорт обезвреживает формулы табличных редакторов.
  6. **Интерфейс, собранный заново** — верхняя навигация (без сайдбаров),
     hash-роутинг, схема группы (ствол, ветки, линии толщиной по трафику,
     перетаскивание для смены порядка), редакторы в выдвижной панели, «Test a
     visitor», Tools, Automation, одна панель сохранения с черновиками, которые
     переживают навигацию. У потоков появились заметка и переопределение
     Content-Type, группы можно дублировать, потоки — переносить между
     группами, окно уникальности вводится в часах. Проверено в настоящем
     браузере: сценарий из 69 шагов против живой админки (round-trip каждого
     потока и каждой группы через их формы, условия, ссылки, перестановка,
     симуляция, сохранение и обратное чтение, автоматизация, тема) и тест
     перетаскивания на pointer-событиях (10 проверок).
  7. `fetch`: `TestConnectionReuse` сравнивал настроенный транспорт с
     транспортом по умолчанию, что зависит от планировщика и падало на
     загруженном CI-раннере; теперь он проверяет границу, которую настроенный
     транспорт гарантирует.
  8. Пропускная способность сравнена с `main` на одной машине под одной
     нагрузкой (`ab`, 50 keep-alive соединений, гео-базы загружены, без Redis и
     ClickHouse): `main` около 110 тыс. запр/с, эта ветка 118–163 тыс. за три
     прогона — шумно, но регрессии нет, так что цифры в README остаются в силе.
- **2026-09-30 — группы читаются словами** (только админка; формат конфига и
  движок не менялись):
  1. **Условия — фразы с чипами.** «organization contains amazon, google,
     hetzner +4» вместо `/amazon|google|…/i`; у стран флаги; текстовые условия
     говорят `contains`, выражения — `matches`. В редакторе значения — чипы
     (Enter, запятая или вставленный список), а не строка через запятую.
     Выражение, которое состоит только из вариантов, показывается и правится
     как слова и сохраняется тем же выражением, с флагами, а нетронутое —
     байт в байт; настоящее выражение правится как текст. Роутер читает `raw`,
     поэтому именно он решает, выражение ли это.
  2. **Выражение, которое движок не может использовать, ловится.** RE2 не
     компилирует lookaround и обратные ссылки, а шаблон, который не
     компилируется, никогда не совпадает — при `is` это отсекает всех
     посетителей. Редактор называет проблему прямо при вводе, схема помечает
     чип.
  3. **Выводы — это строки.** Варианты (`|||` в конфиге) — по строке на каждый,
     выбор «какой вариант получит визит» показывается, только когда их
     несколько, и словами; схема перечисляет их по одному в строке и
     подсвечивает макросы. То же для вывода ботам и выхода группы по умолчанию.
     Правила перезаписи прокси (строки `find|||replace`) — строки «найти →
     заменить», и показываются там, где действуют (тип «Proxy a page»). Поля,
     которые тип не использует, скрыты и сохраняют значения.
  4. Мелочи: лимиты читаются «50 per hour», расписания — «weekdays»; неделя
     начинается с понедельника; алиасы — чипы и при сохранении проверяются как
     ID; при открытой панели плашка сохранения стоит рядом с ней, над затемнением,
     так что клик по Save сохраняет, а не закрывает панель.
  5. Функции, которые переводят хранимые значения туда и обратно, собраны в
     один блок страницы, который `web_logic_test.go` запускает под node
     (`-tags=uitest`): списки слов ↔ выражения, флаги, экранирование, варианты,
     перезаписи. В браузере против стенда: сценарий 105/105 (каждая группа через
     редактор без правок оставляет каждое условие байт в байт; регистрозависимое
     `/Buy|buy/` сохраняет оба слова при правке другого поля), перетаскивание
     10/10.

- **Фикс (ревью кода, 2026-08-20):**
  1. **Паника на подобранной cookie ротатора.** `ztrot_<group>_<stream>` пишет
     движок, но возвращает её посетитель. Отрицательное значение (`-5`) давало
     отрицательный индекс в списке вариантов `|||` и роняло запрос: проверялась
     только верхняя граница. Индексы из cookie и из Redis-счётчика `evenly`
     теперь проходят через `variantIndex()` (`main.go`), который на любом
     значении вне диапазона начинает цикл заново.
  2. **CSV-экспорт логов молча отдавал одну страницу.** `handleLogsExport`
     просил 50000 строк, а `CH.Logs` резал всё больше 1000 обратно до 100.
     Потолок стора теперь равен размеру экспорта (`maxLogRows`), а пагинация
     интерактивного эндпоинта переехала в админский слой (`maxPageRows`) —
     теперь оба лимита означают то, что написано (`clickhouse.go`, `admin.go`).
  3. **Счётчики лимитов могли превращаться в вечный бан.** `Firewall` ставил TTL
     только при положительном окне, поэтому включённый файрвол с `seconds: 0`
     оставлял бессмертный ключ в Redis и блокировал IP навсегда. То же самое —
     для лимита потока типа 2 без периода. Счётчики идут через `incrWithTTL()`,
     который гарантирует expiry (`redis.go`). *С #14 помощник — один атомарный
     Lua-скрипт (`INCR` + `PEXPIRE`); прежняя компенсация «удалить ключ при
     неудачном `EXPIRE`» ушла, потому что компенсировать больше нечего.*
  4. **`save_ip` дописывал дубли до следующего hot-reload.** Дедуп шёл по
     индексу в памяти, который обновляется раз в минуту, поэтому каждый хит с
     того же IP краулера добавлял ещё строку в `ip_<se>.dat`. Множество на
     уровне процесса (`savedBotIPs`) ограничивает это одной записью на IP
     (`bots.go`).
  5. Ключ `?api=` сравнивается через `security.EqualTokens`, а не `!=`
     (`api.go`) — так же, как все остальные секреты в проекте.
  6. `chance` разыгрывается через `hitPercent()`, а не повтором выражения
     `rand.Intn(100)+1` вручную — того самого, чей off-by-one уже однажды
     чинили в `api_mac` (`handler.go`).

  Регресс-тесты: `cmd/engine/rotator_test.go`, `cmd/engine/savebotip_test.go`,
  `internal/store/firewall_ttl_test.go`, `internal/store/loglimit_test.go`,

- **Hot-reload конфига групп (2026-08-20):** движок перечитывает
  `KUZTDS_GROUPS_FILE` при изменении и атомарно подменяет его — по тому же
  тикеру `KUZTDS_RELOAD_INTERVAL`, что и `.dat`-списки; у `config.Groups.Replace`
  наконец появился вызывающий. Правки из админки вступают в силу без рестарта.
  Битый или пропавший файл пропускается и пробуется снова, работающий конфиг
  остаётся на месте, а ip_list-файлы, на которые ссылается новый поток,
  загружаются *до* подмены — фильтр никогда не включается, указывая на не
  прочитанный список. `cmd/engine/reload.go` + `reload_test.go`.

- **Проход по надёжности (2026-08-27 → 2026-09-07; #13, #14, #16–#19, #21–#25,
  #27 — #15 перекрыт #24, #20 и #26 закрыты без мержа).** Сгруппировано по тому,
  что
  каждое защищает:

  *Горячий путь, корректность.* Неудачный CURL-запрос больше не отдаётся как
  нормальная страница — раньше тело чужой ошибки рендерилось под нашей
  двухсоткой и писалось в лог как обычный показ (#13). Значение `[REMOTE]`
  подставляется **после** `render.Expand`, поэтому партнёр, вернувший
  `[RANDLINE-(secret.dat)-1]`, больше не может заставить движок прочитать файл
  из data-каталога и отдать его (#18). Лимит потока забирается одним атомарным
  шагом вместо «прочитать, потом инкрементить», что перебирало примерно на
  величину конкурентности — 114 показов на лимите 100 при 64 горутинах, ровно
  100 после (#14).

  *Нагрузка и время жизни.* logbuf копит и вставляет разными горутинами, поэтому
  медленный ClickHouse больше не ослепляет буфер со скоростью его полного
  отсутствия; у остановки один владелец и два последовательных бюджета, а
  переполненная очередь батчей — отдельная причина потерь, `Losses.Queue` (#19).
  Кэш fetch ограничен по байтам и вычищает истёкшее — его ключи несут
  `[IP]`/`[CID]`/`[PAR-n]`, то есть он рос на запись с посетителя вечно (#24). У
  HTTP-клиента настоящий транспорт с потолком исходящих: в `net/http` по
  умолчанию 2 idle-соединения на хост и никакого предела одновременным (#16).
  Списки separation держатся в памяти, а не читаются с диска на каждый запрос
  (#17).

  *Админка.* Усиление логина — `SECURITY.md` §3 (#21, #22, #23 через #25).

## Как запустить заново (дев)
```bash
cd kuztds
make infra-up                         # ClickHouse + Redis
go run ./cmd/admin -hash 'admin123' > /tmp/admin.hash   # хэш пароля

# движок :8080
KUZTDS_DATA_DIR=../database KUZTDS_GROUPS_FILE=configs/test_groups.json \
KUZTDS_TRUSTED_PROXIES=127.0.0.1/32 KUZTDS_POSTBACK_KEY=pbsecret KUZTDS_API_KEY=apikey123 \
KUZTDS_KEYS_DIR=/tmp/kuztds-keys KUZTDS_GEO_DB=internal/geo/testdata/GeoLite2-City-Test.mmdb \
KUZTDS_REDIS_ADDR=localhost:6379 KUZTDS_CLICKHOUSE_ADDR=localhost:9000 \
KUZTDS_CLICKHOUSE_DB=kuztds KUZTDS_CLICKHOUSE_USER=kuztds KUZTDS_CLICKHOUSE_PASSWORD=devpassword \
go run ./cmd/engine

# админка :8090 (admin / admin123)
KUZTDS_ADMIN_PASSWORD_HASH="$(cat /tmp/admin.hash)" KUZTDS_ADMIN_PASSWORD_FILE=/tmp/admin.hash \
KUZTDS_ADMIN_COOKIE_SECURE=false KUZTDS_ENGINE_URL=http://localhost:8080 \
KUZTDS_GROUPS_FILE=configs/test_groups.json KUZTDS_DATA_DIR=../database KUZTDS_KEYS_DIR=/tmp/kuztds-keys \
KUZTDS_REDIS_ADDR=localhost:6379 KUZTDS_CLICKHOUSE_ADDR=localhost:9000 \
KUZTDS_CLICKHOUSE_DB=kuztds KUZTDS_CLICKHOUSE_USER=kuztds KUZTDS_CLICKHOUSE_PASSWORD=devpassword \
go run ./cmd/admin

# cron (опционально; добавь KUZTDS_CRON_FILE / KUZTDS_GEO_DB / KUZTDS_ASN_DB и админке,
# а два гео-пути — движку)
KUZTDS_CRON_FILE=/tmp/kuztds-cron.json KUZTDS_DATA_DIR=../database KUZTDS_KEYS_DIR=/tmp/kuztds-keys \
KUZTDS_GROUPS_FILE=configs/test_groups.json \
KUZTDS_GEO_DB=/tmp/kuztds-geo/city.mmdb KUZTDS_ASN_DB=/tmp/kuztds-geo/asn.mmdb \
KUZTDS_CLICKHOUSE_ADDR=localhost:9000 KUZTDS_CLICKHOUSE_PASSWORD=devpassword \
go run ./cmd/cron
```
Схема ClickHouse применяется автоматически из `migrations/clickhouse/*.sql` на
свежей базе; на существующей движок и админка сами добавляют новые колонки при
старте.

## Заметки
- Админка и движок должны указывать на ОДИН `KUZTDS_GROUPS_FILE`. Админка читает
  и пишет его live; движок перечитывает его при изменении, по тикеру
  `KUZTDS_RELOAD_INTERVAL`. Рестарт не нужен.
- Группа: `id` = идентификатор и адрес `/<id>`; `name` — опциональное отображаемое имя.
